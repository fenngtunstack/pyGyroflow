# 把Rust算法移植到Python，我用四级验证堵住了所有怀疑

把Gyroflow的Rust稳定算法逐行翻译成Python，这件事我干了几周。代码写完只是起点——怎么证明Python版本和Rust原版行为一致？这篇文章讲我设计的四级验证体系，以及移植过程中踩到的6个坑。

## 为什么需要四级验证

算法移植的验证有一个核心矛盾：你不可能用一种测试覆盖所有风险。单元测试能验证函数级正确性，但管不了跨模块交互；集成测试能跑通管线，但可能恰好跳过了精度敏感的路径；端到端测试最接近真实使用，但debug成本最高，定位问题最难。

所以我按风险层级设计了四级结构：

- Level 1 单元测试：验证每个函数在已知输入下的输出
- Level 2 Rust-Python黄金对比：用同一组合成数据，对比两个实现的数值结果
- Level 3 管线集成测试：模块串起来跑完整流程
- Level 4 端到端验证：视频级对比，逐帧算PSNR/SSIM

这不是过度工程。每级验证都抓到了前一级没抓到的问题。

## Level 1: 144个单元测试

144个测试覆盖了12个模块：四元数运算(28)、IMU积分(15)、平滑算法(8)、镜头畸变模型(22)、帧变换(4)、滤波器(9)、关键帧(15)、GyroSource(15)、镜头参数(14)、StabilizationManager(6)、渲染(3)、缩放(5)。

数量看起来多，但四元数相关的测试就占了将近一半。原因是四元数有一个容易忽略的特性：**double cover**。

`q`和`-q`表示同一个旋转。这听起来是常识，但在实际测试中坑死人。比如你生成一个期望四元数`q = [0.707, 0, 0.707, 0]`，Python实现算出来的是`[-0.707, 0, -0.707, 0]`。数值上完全不同，逻辑上完全等价。如果直接做逐元素对比，测试必挂。

<!-- ✏️ 编辑建议：在这里加一个你自己遇到的double cover踩坑经历，或补充你项目中类似的设计决策 -->

所有四元数对比测试都要先处理double cover：

```python
def quat_eq(q1, q2):
    # 取点积，负数说明是-flip
    if np.dot(q1, q2) < 0:
        q2 = -q2
    return np.allclose(q1, q2)
```

这行代码不处理好，后面所有级别的验证都会被假阳性或假阴性淹没。

## Level 2: Rust-Python黄金对比——为什么必须有这一级

Level 1验证的是Python函数本身的逻辑正确性，但它回答不了一个关键问题：Python实现的行为和Rust原版在数值上到底有多接近？

这一级的设计思路是：用完全相同的合成IMU数据（加速度计+陀螺仪+时间戳），分别喂给Rust实现和Python实现，对比输出的四元数序列。Rust侧用nalgebra线性代数库和ahrs crate，这是Gyroflow原版的依赖。

5个积分器（simple_gyro_accel、mahony、madgwick、complementary、simple_gyro）全部PASS，最大误差在`1e-15`量级——也就是机器精度（double的epsilon约`2.22e-16`）。这意味着Python移植版本和Rust原版在数值上是等效的。

Rust侧的黄金数据生成器放在`msGyroFlow/crates/msgyro-golden-gen/`，用`cargo build --release`构建。它输出一组标准化的`(timestamp, quaternion)`对，Python侧读进来逐帧对比。

这一级测试抓到的bug最多，也最隐蔽。下面展开讲。

## 移植中发现的6个坑

这些都是在Level 2黄金对比中暴露的。Level 1的单元测试全部通过，但黄金对比一跑就挂。

### 坑1: 加速度归一化时机错误

`simple_gyro_accel`这个积分器里，加速度计数据有个合法性检查：原始模长在0.9到1.1之间才算有效（假设单位重力向量）。

Python版本我按原始数据检查模长，过了。Rust版本先对向量做了`normalize()`，归一化后模长永远是1.0，检查当然永远通过。行为不一致。修正方法：Python侧也改为先检查原始模长，再归一化。

### 坑2和3: Mahony积分器的两个bug

Mahony滤波器有两个独立的问题。

索引混淆：nalgebra库内部存储四元数用`[x, y, z, w]`顺序，但对外接口（构造函数、getter）用`[w, x, y, z]`顺序。移植时按接口文档写，但内部计算直接索引了数组，顺序就反了。这种错误单元测试很难发现——因为测试数据也是按接口构造的，错上加错反而对了。

<!-- ✏️ 编辑建议：在这里补充你遇到过的类似"接口和内部表示不一致"的经历 -->

时间单位混用：`prev_time`在某些路径下是毫秒，某些路径下是秒。Rust原版里用类型系统（不同struct的field）做了一定程度的区分，但Python没有这种类型保护，直接`float`到底。混用的结果就是积分步长`dt`差了1000倍，Mahony的增益参数效果完全不同。

### 坑4: Madgwick的Jacobian笔误

Madgwick算法需要计算目标函数的Jacobian矩阵。第3行有一个元素应该是`2*z`，Rust代码里写的是`2*y`。

这个错误是原作者的代码里就存在的。翻译成Python后，因为做了黄金对比才发现。直接照抄Rust代码反而是错的——黄金对比的正确性锚点是Rust的实际运行输出，不是Rust源码的字面含义。源码写`2*y`，运行结果就包含了这个bug；Python翻译也写`2*y`，两边结果一致，对比PASS。但如果你按论文推导发现应该是`2*z`然后"修正"了，反而会挂。

这引出一个设计选择：黄金对比到底比的是"和Rust行为一致"还是"和论文理论值一致"？我选了前者。移植阶段的目标是行为对齐，算法本身的正确性是另一个课题。

### 坑5和6: Complementary滤波器的坐标系差异

Complementary滤波器有两个相关问题。

坐标系不同：Python版本用的是body-frame correction（机体系修正），Rust版本用的是world-frame（世界系）。两者在数学上是等价的，但需要通过旋转矩阵转换。数值路径完全不同，直接对比必挂。

权重公式不同：同样的参数名，Rust和Python的计算方式不一样。这不是bug，是两个版本独立实现时的设计选择。黄金对比时需要对齐权重计算逻辑。

## 时间戳容差：浮点精度的隐藏陷阱

还有一个容易忽略的问题：时间戳对齐。

IMU数据里的`timestamp_ms`是浮点数，Python侧要转成微秒整数做插值：`int(timestamp_ms * 1000.0)`。浮点乘法有精度损失，同一个`timestamp_ms`值在Python和Rust里算出来的整数可能差1。比如`1234.567 * 1000.0`，Python算出`1234567`，Rust可能算出`1234568`。

解决方案是用最近邻匹配代替精确匹配，容差设为2微秒。这个容差已经足够覆盖浮点转换误差，同时又不会导致错误的时间戳关联（IMU采样率通常在200-1000Hz，相邻采样点间隔1000-5000微秒）。

## Level 3和Level 4: 更上层的验证

Level 3做管线集成：Python内部的模块串起来跑完整的StabilizationManager流程，加上Python自比黄金测试（不依赖Rust，只验证Python端内部一致性）。

Level 4是端到端验证：用PyGyroFlow和Gyroflow分别处理同一段视频，逐帧计算PSNR和SSIM。这一级目前还在完善中。理论上如果Level 2已经证明数值精度在机器精度级别，Level 4的差异应该只来源于GPU渲染的实现差异。实测也验证了这一点：同一帧的GPU和CPU渲染结果，像素值差异在2个灰度级以内，属于ULP（Unit in the Last Place）级别的浮点误差。

## 验证体系的实际回报

回顾整个移植过程，四级验证的价值在于：每升一级，就排除了一类错误的可能性。Level 1过了说明单个函数没写错；Level 2过了说明和Rust行为对齐；Level 3过了说明模块间交互没问题；Level 4过了说明最终产物可用。

而那6个坑，全部是Level 2抓到的。没有黄金对比，Level 1的144个测试全绿也不会给我移植正确的信心。单元测试只能验证你理解了算法，黄金对比才能验证你和原版行为一致。

这大概是算法移植中最值得投入的工程实践：不要相信"逻辑上等价"的代码，用数据说话。
