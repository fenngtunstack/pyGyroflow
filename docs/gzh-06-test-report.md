# 把Rust陀螺仪算法搬到Python，我踩了5个坑才跑通

最近在做一个项目：把Gyroflow的核心陀螺仪 stabilization算法从Rust移植到Python。动机很直接——Python生态里有更多的数据处理和机器学习工具，但Gyroflow的稳定算法是纯Rust写的，想用就得重写。

移植完成后跑了 198 个测试用例（pytest 收集），192 个通过，5 个跳过，1 个预期失败（GPU uint8 路径已知损坏，标 xfail）。听起来基本顺利，但通过的测试背后是几个非常典型的数值计算陷阱，值得单独拿出来讲。

## 数值一致性的验收标准

先说结果。移植的核心目标是数值一致性——Python实现和Rust原版的输出差异必须在可接受范围内。容忍度定在1e-6。

实际跑出来的结果：

| 算法 | 最大误差 |
|------|----------|
| simple_gyro | 5.44e-15 |
| simple_gyro_accel | 2.22e-15 |
| mahony | 5.83e-16 |
| madgwick | 9.99e-16 |
| complementary | 4.33e-15 |

全部在机器精度级别，比容忍度低了9个数量级。这不是巧合，是逐个修bug修出来的。

## 坑1：加速度归一化的时序问题

simple_gyro_accel是最基础的融合算法，只用陀螺仪和加速度计。移植时直觉上先把代码搬过来，测试一跑，误差远超预期。

排查后发现，归一化操作的位置不对。Python版本在某个中间步骤之后才做normalize，而Rust版本在数据进入计算流程之前就统一归一化了。这是一个很隐蔽的问题——数学上看起来等价，但浮点运算不满足结合律，运算顺序的改变会累积误差。

修复方法：把加速度归一化统一到计算流程的最前面，和Rust保持一致。

这个坑的教训是：浮点数运算不是数学，`a*(b*c)` 和 `(a*b)*c` 在计算机里不是一回事。移植数值代码时，运算顺序必须严格对齐，不能想当然地"优化"。

## 坑2：四元数内部格式的索引陷阱

这是整个移植过程中最隐蔽的一个bug。

Mahony滤波器在计算过程中需要用到四元数表示的重力方向。Rust版本用nalgebra库的四元数类型，Python版本用SciPy的`Rotation`。

问题出在：nalgebra的四元数内部存储格式是`[x, y, z, w]`，但它的对外接口（构造函数和访问器）用的是`[w, x, y, z]`。这两套索引不一致。Python移植时直接用接口的直觉顺序去索引内部数组，导致重力向量的x、y、z分量实际上取错了位置。

这个bug的表现很可怕：误差不是固定的，而是随时间累积。前几秒看起来正常，越跑越偏。因为重力向量算错了，姿态校正的方向就是错的，每一步都在往错误的方向修正。积分器把误差越滚越大。

修复方法：重写重力向量的计算公式，确认每个索引对应的是哪个分量。不要依赖库的"直觉"接口，直接看源码确认内存布局。

这个坑的教训是：跨语言移植时，数据结构内部的内存布局是最大的隐患之一。不同的库对同一个数学对象（四元数、矩阵）的内部表示可能完全不同，而且文档未必明确写出来。遇到这类问题，最可靠的方法是构造一个已知输入，两边分别打印中间结果，逐字段对比。

## 坑3：时间单位的统一

还是Mahony算法。`prev_time`变量在Python里用的是秒，Rust里用的是毫秒。差了一个数量级，而且是1000倍。

这看起来很低级，但实际上很容易踩。Python的`time.time()`返回秒，Rust的`Instant::now().elapsed().as_millis()`返回毫秒。两个生态的默认时间单位不同，移植时如果不专门处理，就会引入一个系数偏差。

这个bug的影响是积分步长计算错误，导致陀螺仪的角速度积分结果偏移。在短时间内看不出来，长时间运行后姿态会明显漂移。

修复方法：统一用秒作为内部时间单位，在数据进入算法之前做一次转换。

## 坑4：Jacobian矩阵的手写错误

Madgwick算法的核心是梯度下降，需要手写Jacobian矩阵。这个矩阵不大，但每个元素都是关于四元数分量的多项式。

Python版本在Jacobian的第3行写错了一个系数：应该是`2*z`的地方写成了`2*y`。一个字母之差。

这种错误的特征是：单步误差很小，但梯度方向是错的。Madgwick算法在每一步都沿着梯度方向做一步下降，梯度方向偏了，收敛方向就偏了。最终表现是姿态估计的稳态误差变大，但不会像Mahony的索引错误那样发散。

排查方法是：把Jacobian矩阵的每个元素单独拿出来，和Rust版本做逐元素对比。发现第3行第4列的系数不对，改过来就好了。

这个坑的教训是：手写数学公式到代码是最容易出错的环节之一。符号推演时很清楚，一旦变成代码，下标和系数特别容易抄错。最好的防御措施是：对每个公式都写一个单元测试，用已知输入和已知输出验证，而不是只靠端到端测试。

## 坑5：完全不同的校正策略

Complementary滤波器是5个bug里最"离谱"的一个。

初始Python实现用的是body-frame校正——在物体坐标系下做加速度计和陀螺仪的融合。Rust原版用的是world-frame校正——在世界坐标系下做融合。两种策略从数学框架上就不一样，不是"实现细节不同"，而是"思路完全不同"。

body-frame的方式在直觉上更容易理解：传感器数据是物体坐标系下的，直接在那个坐标系下做融合很自然。但Gyroflow的Rust实现选择了world-frame，原因是它和后续的稳定管线对接更方便。

这个问题不是"bug"，是"理解偏差"。移植时没有深入理解Rust版本的设计意图，按照自己的直觉实现了"看起来对"的版本。端到端测试一跑，误差比其他算法大了好几个数量级。

最终重写了整个校正逻辑，改为world-frame方式，误差立刻降到机器精度级别。

这个坑的教训是：移植代码之前，先理解原作者的设计选择。不要只看代码表面的数学公式，要看为什么选这个框架而不是另一个。很多时候"看起来等价"的两种实现在工程上的表现天差地别。

## 跳过的5个测试

有5个测试没跑。1个是PyAV对不存在文件的处理，Python版本的行为和Rust不完全一致，属于边界case。另外4个是GoPro、Sony、Insta360的特殊telemetry解析，需要对应硬件采集的真实数据，没有这些数据就只能跳过。

这些不影响核心算法的正确性验证。

## 一些感想

做数值计算相关的跨语言移植，最难的不是"翻译"代码，而是两个语言生态在底层数据表示上的差异。四元数的内存布局、时间单位、浮点运算顺序——这些都是"正确但不同"的实现选择，不是对错之分。

另一个感受是：单元测试在数值计算项目里的价值远超一般项目。5个bug里，3个是靠单算法的精度测试发现的。如果只做端到端的"视频输入-稳定输出"对比，大概率能跑出看起来不错的结果，但误差来源根本无从判断。

测试环境是Python 3.12.13，NumPy 2.4.6，SciPy 1.17.1，PyAV 17.0.1，OpenCV 4.13.0，pytest 9.0.3。全部跑完12.3秒。
